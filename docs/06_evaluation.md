# Dataset Split & Evaluation Discipline

## The split

| Set | Path | Seed | n | Corpus label | Purpose |
|---|---|---|---|---|---|
| **Dev** | `data/dataset/dev/` | `42` | 500 | `dev` | Free to inspect, analyze, and use for any design/tuning decision |
| **Eval (held-out)** | `data/dataset/eval/` | `777001` | 1,000 | `test` | **Sealed** — see rules below |

Both generated by `scripts/generate_data.py` (same generator, same distribution
parameters — `METHOD_WEIGHTS`, `REASON_WEIGHTS`, `RECURRING_RATE`,
`LATENT_CLASS_WEIGHTS`, etc.). Only the seed and target size differ. Regenerate
with:

```
python scripts/generate_data.py --seed 42     --n 500  --corpus dev  --scenario S1 --out data/dataset/dev
python scripts/generate_data.py --seed 777001 --n 1000 --corpus test --scenario S1 --out data/dataset/eval
```

Both are pure functions of `(seed, n, ...)` — re-running either command reproduces
byte-identical output, confirmed this session for the dev set across two independent runs.

## Validation status

Both sets pass `scripts/validate_data.py` (missing values, invalid values,
duplicates, impossible states, temporal consistency, class-support thinness) as of
this document's writing:

- **Dev**: 0 FAIL, 0 WARN.
- **Eval**: 0 FAIL, 0 WARN.

Structural validation of the eval set is **not** a violation of the held-out rule
below — confirming a dataset is well-formed (no duplicate IDs, no orphaned ground
truth, no impossible states) is a data-quality gate, not a modeling decision. It
does not touch class distribution, diagnosis accuracy, or any policy outcome.

## What "must not influence model rules or thresholds" means, precisely

The object being protected is **`agent/policy/rules.yaml`** (attempt caps, downtime
deferral parameters, and every currently-disabled rule reserved for Phase 2/3) and
**any future calibration fit** (Phase 3's confidence calibrator). None of these have
been touched in response to anything observed from `data/dataset/eval/`, and the
commitment going forward is that they never will be — no threshold, weight, or rule
constant in this repository may be justified by "because the eval set showed X."

### What I have already seen, stated plainly rather than glossed over

Running `scripts/generate_data.py` against the eval seed necessarily printed its
own summary line to the console: method mix (~56% UPI / 17% card / 18% emandate /
9% netbanking), customer/mandate counts, and ambiguity split (590 CLEAN / 410
AMBIGUOUS out of 1,000). This is disclosed here rather than pretended away.

The distinction that matters: **generator parameters** (`METHOD_WEIGHTS`,
`REASON_WEIGHTS`, `RECURRING_RATE`, `LATENT_CLASS_WEIGHTS`) were fixed *before*
either dataset was drawn, and are properties of the data-generating process, not
policy thresholds. Seeing the eval set's resulting distribution does not let me
tune parameters that were already fixed prior to generation, and it has not
informed any change to `rules.yaml`. Beyond the one console line above and the
`0 FAIL / 0 WARN` structural-validation summary, no further inspection of
`data/dataset/eval/` was performed — its `ground_truth.HIDDEN.json` class breakdown,
diagnosis-accuracy potential, or per-record content have not been examined.

### Rules going forward

1. **No `rules.yaml` edit may cite eval-set behavior as justification.** Cite
   `EVIDENCE.md`, `DECISIONS.md`, or dev-set evidence instead.
2. **No generator-parameter change** (`scripts/generate_data.py`'s weight tables)
   **may be justified by eval-set output.** Changing them changes the eval set
   itself, which would need a fresh seed and a fresh version of this document.
3. **The eval set is scored, not explored.** Any future `evalharness`-style run
   against `data/dataset/eval/` should log a `times_scored` counter (the same
   discipline `eval/PREREGISTRATION.md` established for the internal SQLite
   corpus) and treat repeated scoring as validation-set behavior, not held-out
   behavior, past the first real evaluation.
4. **If the seed or generator version must ever change,** it is a new eval set,
   and this document's seed/date must be updated to match — never silently swapped.
5. **Calibration (Phase 3) fits on the dev set (or a further dev/calibration split
   within it), never on eval.**

## Relationship to the other corpus artifacts in this repo

This is the third, and now canonical, dataset lineage in the repository — worth
distinguishing explicitly since the other two exist for different purposes and
should not be confused with this split:

| Artifact | Built by | Purpose |
|---|---|---|
| `data/dev.db` | `scripts/gen.py` + `datagen/generate.py` | Feeds the **live SQLite pipeline** (`agent.pipeline.ingest`) for the internal eval harness (`evalharness/run.py`) — a different generator with its own distribution choices, documented in `docs/00_project_state.md` |
| `data/dataset/dev/`, `data/dataset/eval/` | `scripts/generate_data.py` | **This split.** Portable JSON, schema-validated, generator-agnostic to any particular pipeline |
| `eval/PREREGISTRATION.md`'s corpora A/B/C | Not yet built | The Phase 3 plan (dev=300/calibration=500/**sealed test=1,000**) — this document's eval set is deliberately sized (n=1,000) and seeded to be usable as that sealed corpus C if `datagen/generate.py` and `scripts/generate_data.py` are ever unified, but they are **not yet the same artifact** and should not be assumed interchangeable without re-validating that unification explicitly
